# M7-W01-C02-T2 — finite tensor adoption and integration boundary decision

## Question

Can Math responsibly admit a new public dense or sparse tensor engine, an implicit broadcasting contract or a managed/native tensor provider today? Which bounded shape, ownership and source-free consumer evidence is necessary, and how is an explicit non-admission decision reexamined?

## Observation

- RS108 `docs/planning/evidence/M7-W01-C02-T1-qualified.json` records two independent BCL-only oracle groups. A declared rank-three shape `[2,2,2]` and row-major values `[1,2,3,4,5,6,7,8]` yield sum `36` and element `[1,0,1] = 6`.
- The finite research budget is `64 elements / 512 bytes`: `[4,4,4]` exactly reaches 64 while `[4,4,5]` exceeds it. Zero extent, invalid rank and huge dimensions are rejected before allocation. `[2,2,2]` and `[2,4]` have equal element counts but incompatible rank/shape; equal storage is not reshape or broadcast permission.
- `docs/planning/decisions/m7-w01-c02-provider-screen.md` screens existing Math arrays/matrices, managed dense, sparse/graph, third-party managed and native/GPU choices. No external provider version/source SHA, package rights/notices, net10.0 runtime/RID, independent source-free consumer, API contract or distinct consumer demand was actually qualified.
- Existing Matrix and finite numerical functionality remains available through its own previously admitted Math contracts. The separate M7 C01 precision provider review ended in deferral. Neither observation establishes tensor demand or certifies arithmetic or physical uncertainty.
- Independent `docs/planning/ValidateM7TensorBoundary.cs` audits prior T1 SHA-256 provenance, accepted shape refusals, this negative-gate decision and DWF product/native lifecycle. The original independent T1 oracle is rerun before the T2 document transition, not presented as new product functionality.

## Decision — explicitly defer tensor API/provider admission

**DEFER any new public Tensor API, new advanced package, broadcasting/sparse/GPU backend and third-party managed/native provider.** Keep the already qualified Math engines. This completes a *research spike*, not a tensor implementation or a permanent veto.

The three mandatory **review triggers** for any future owner-authorized tensor admission are:

1. **Demonstrated consumer gap:** identify an actual Math consumer, missing finite tensor operation, rank/shape/element type and reproducible example that existing arrays/matrices cannot satisfy.
2. **Bounded resource and semantic contract:** specify rank/shape/strides, element and byte caps, checked multiplication, aliases, cancellation, deterministic invalid-shape/overflow/budget failures, no silent broadcasting/reshape/copy, and a realistic maintenance/performance budget.
3. **Independent provider and recipient qualification:** if a new engine is justified, pin exact source/commit/version, license/transitive/native notices, redistribution rights, net10.0/RID, offline restore and rollback, independent exact shape/oracle corpus, and isolated source-free consumer tests before any cutover.

All three gates must be satisfied before admission is *considered*; a trigger does not itself grant approval. When evidence is absent, remain deferred and retain the qualified Math interfaces.

## Ownership and explicit limits

- Math owns mathematical representation and finite calculations, not AURA job scheduling, agent execution policy, UI rendering or resource orchestration.
- Data-layout rules are not automatic physical-unit conversion, numerical error certification, statistical confidence or a proof of sparse/ML/GPU support.
- The research-only limit `64 elements / 512 bytes` is an oracle budget, not a published product API guarantee.
- No external provider was installed, no public NuGet was published, no sibling repository was modified, no `dw.discovery` or Decision/AURA/MCDM adoption was authorized.

On success, C02 becomes **done as a spike**, while M7-W01 and M7 stay **in-progress**.
