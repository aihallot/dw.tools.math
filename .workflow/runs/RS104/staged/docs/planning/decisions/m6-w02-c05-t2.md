# M6-W02-C05-T2 — provider adoption and distribution boundary decision

## Question

Can Math close the optional scientific-family adoption task without external owner approval, and which exact semver, notice, source pin and disposition gates must remain enforceable before any later replacement, reuse, removal or release?

## Observation

- RS103 qualified seven historical family contracts, each with an independent oracle, source SHA-256, recorded family preview version and bounded numerical domain. Source: `docs/planning/evidence/M6-W02-C05-T1-qualified.json`.
- RS102 qualified a **local**, BCL-only `dw.tools.math.scientific` package `1.1.0-preview.14`, size 37,270 bytes, SHA-256 `2de3e9f536ced58e28d1558ff7c4692f367b72d5efaa1989d56ffa8ec07a31cf`, with seven isolated source-free consumer receipts, eight probes each. These are historical receipts; T2 runs no new scientific tests and does not rebuild this package.
- The qualified observation is bounded to the recorded .NET SDK/runtime and host. No Linux/macOS execution, public NuGet publication, portable ABI, certified error bound or downstream integration follows from that receipt.
- `docs/distribution/m5-package-notices.md` records source ownership without selecting a new open-source license or granting general public redistribution. Math's existing M5 publication boundary explicitly requires owner approval for stable/public releases.
- `docs/planning/requests/decision-bounded-bracketed-root-assessment.md` is a proposal for review, not evidence of Decision duplication, delivered transmission, consent, product adoption or a migration.

## Decision

Keep **all seven** admitted families and their source/provider identities unchanged in Math. No automatic external cutover, no replacement, no package publishing and **no family removal** are approved. This is a documented *retain-and-defer* disposition, not a claim of affirmative external owner acceptance.

For any future adoption, replacement or removal, require a new owner-authorized DWF run that provides, together:

1. **Owner disposition** naming the exact family, API and action (retain, adopt, replace or remove), with an explicit authorization record. Silence defaults to retain; no inferred approval.
2. **Immutable provenance**: source revision and SHA-256, historical family admission, exact candidate package version/length/SHA-256, target runtime/RID, and provider/license/transitive-dependency identity. Requalification is required when bytes or support target change.
3. **Compatibility/semver review**: compare current and proposed public API and behavior, failure statuses, limits, units, binary64 assumptions, and consumer expectations; justify major/minor/patch/prerelease treatment and any migration/rollback path before changing package or contract.
4. **Notices/rights review**: establish source redistribution rights, third-party attributions and packaging notices, with owner approval for any stable/public distribution. Existing owner attestation is not a general public-release permission.
5. **Independent verification**: affected exact-oracle and refusal tests, locally restored source-free consumer against the candidate package, relevant cross-family regression, target OS/runtime qualification, and explicit publish/adopt authorization before cutover.

The bounded scalar bracketed-root assessment remains an **unsent owner-triage candidate**. No Decision duplicate is established. Decision, AURA, MCDM and dw.discovery remain unchanged.

## Acceptance and lifecycle

C05-T2 is a **documentary** boundary and integration task. Its acceptance is a reproducible retain/defer matrix, immutable historical pins, explicitly separated compatibility/notices/owner gates, and a no-cutover decision. These conditions permit closure of the C05 document phase and, if all accepted W02 phases are done, the W02 work package. The separate **G-M6 release gate** remains open; closing this document is **not** closing M6, publishing `1.1.0`, or authorizing external migration.

## Alternatives and follow-up

Reject silent semver bumps, public license assumptions, automatic removal, cross-repository writes, and treating archived RS102 science as new T2 execution. Next: independently qualify the M6 release gate using durable local package/consumer evidence, rights and owner boundaries; then decide M6 closure versus explicit outstanding blockers.
